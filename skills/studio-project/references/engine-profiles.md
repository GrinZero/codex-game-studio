# 引擎适配与资源检查

[返回规范](project-file-guide.md) · [命名速查](asset-naming.md) · 版本 1.2

## 1. 选择适配，不叠加互相冲突的命名

以下规则作用于引擎工程目录，可位于 `game/` 或现有项目根目录。每个引擎工程采用一种适配；制作源文件可共同使用通用命名。按引擎要求保留的目录、元数据与包结构不算违规。

| 项目           | Godot                                      | Unity                                         | Unreal                                                  |
| -------------- | ------------------------------------------ | --------------------------------------------- | ------------------------------------------------------- |
| 项目入口       | `project.godot`                            | 工程根目录                                    | `.uproject`                                             |
| 自有内容根建议 | `res://forest_relics/`                     | `Assets/ForestRelics/`                        | `Content/ForestRelics/`                                 |
| 关卡建议       | `forest_relics/levels/`                    | `Assets/ForestRelics/Levels/`                 | `Content/ForestRelics/Maps/`                            |
| 角色内容       | `characters/ranger/`                       | `Characters/Ranger/`                          | `Characters/Ranger/`                                    |
| 命名默认       | snake_case，用扩展名和用途后缀区分         | 资源可采用通用规则；C# 文件与类名遵循语言约定 | 引擎资产 PascalCase 加类型前缀，源文件可保持 snake_case |
| 基础机制       | 内容根下 `core/`                           | 内容根下 `Core/`；代码也可按程序集边界组织    | 蓝图在 `Content/.../Core/`，C++ 在原生 `Source/` 模块   |
| 插件／外部包   | 保留 `addons/` 等原生结构                  | 保留 `Packages` 与包规定的资产布局            | 保留 `Plugins`、插件挂载点与必要配置                    |
| 不得按缓存误删 | 所用版本需要的资源 UID、导入配置与项目设置 | `.meta` 与项目必要配置                        | 项目配置、资源包及引用关系                              |

现有 Godot 项目直接使用根级 `characters/` 等目录也可保留，记录为项目适配即可。Unity 或 UE 既有大小写、术语和目录别名一致时同样不要求批量迁移。

### 1.1 Godot

- `ranger.tscn`、`ranger_controller.gd`、`ranger_material.tres` 使用共同词根。角色场景留在角色目录，主关卡集中在 `levels/`；不要按 `.tscn` 扩展名将所有场景混放。
- 对同为 `.tres` 的材质、属性、主题等增加语义后缀，避免资源内容不明。节点名、类名、C# 脚本名遵守对应语言与引擎规则。
- 需要通过编辑器运行的 `sandbox/` 保持可导入，同时设置发行排除；不需要导入的源文件、文档可放工程外，或按需要使用 `.gdignore`。被 `.gdignore` 排除的内容不能再作为运行依赖。
- `.godot/` 与需保留的资源身份／导入配置分别处理。忽略规则按实际版本生成或核实，不能跨 Godot 大版本直接复用旧清单。
- `core/` 默认置于项目内容根。已有项目采用指南中的根级 `core/` 时可保留，但应明确其归属、公共接口以及与游戏内容的依赖关系。

### 1.2 Unity

- 保留 `Assets`、`Packages`、`ProjectSettings` 原生职责。自有游戏内容在项目命名空间，外部包遵循包管理器布局。
- `ranger.prefab` 与其专用材质、模型、脚本就近组织；`RangerController.cs` 采用类名大小写，并不违反通用资源文件规则。
- 移动／重命名优先通过编辑器，保留 `.meta` 的资产身份；不要复制文件时丢失或给不同资产复用同一身份。
- `Resources`、`StreamingAssets`、`Editor` 等位置可能具有引擎语义，仅为实际用途建立。不能把所有素材放进 `Resources` 来代替内容组织与加载设计。
- 关卡、可加载资产和实验目录是否参与发行，按项目实际构建和加载配置检查，不能只凭目录名判断。

### 1.3 Unreal

- 原生资产按类型前缀区分，但项目不需要使用源指南的所有类型。以下是本规范的默认 UE 词典；现有一致前缀可记录后沿用。

| 类型             | 引擎内名称示例                                       | 通用制作端对应                                   |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------ |
| 静态网格         | `SM_WoodenChest`                                     | `wooden_chest.glb`／FBX                          |
| 蒙皮网格／骨架   | `SK_Ranger`、`SKEL_Ranger`                           | 角色模型与实际骨架来源                           |
| 可实例化蓝图     | `BP_WoodenChest`                                     | 木箱组件场景／预制体语义                         |
| 动画片段／控制   | `A_Ranger_Run`、`ABP_Ranger`、`BS_Ranger_Locomotion` | `ranger_anim_run` 等                             |
| 材质／实例／函数 | `M_Surface`、`MI_Ranger`、`MF_Wind`                  | 通用材质、角色配置、风函数                       |
| 贴图             | `T_Ranger_D`、`T_Ranger_N`、`T_Ranger_ORM`           | base_color、normal、约定的打包贴图               |
| UI               | `WBP_Inventory`                                      | inventory 界面组件                               |
| 数据表           | `DT_Items`                                           | `items_table`                                    |
| 行为树／黑板     | `BT_Ranger`、`BB_Ranger`                             | 行为逻辑与状态数据                               |
| 特效             | `NS_Fireball`                                        | Niagara System；不把旧粒子类型前缀套用到所有特效 |
| 音频             | `SFX_ChestOpen`、`Music_Forest`                      | 本规范选用明确用途词，避免动画与音频共用 A\_     |

这里选用 `SM_`；Allar 默认表使用 `S_` 并说明也有人用 `SM_`。音频、黑板与特效的示例是本规范的项目选择，不宣称是 Allar 原表或所有 UE 项目的统一标准。`T_*_D` 对应基础色，`T_*_N` 对应法线；其他缩写、ORM 和 Alpha 通道必须写入项目词典。

- 在编辑器内移动资源、修复引用与重定向器；清理空文件夹也遵循此流程。不要通过 Finder／终端批量移动 `.uasset` 后假定引用完好。
- 工程内可保留 Developers 实验区，正式内容不得依赖它；地图、插件内容和调试资源需检查实际打包设置。
- 源文件与引擎资产存在一对多导入时记录映射。例如一个 FBX 导出后可产生网格、骨架和动画；它们不能简单靠扩展名被视为一份资产。

## 2. 跨引擎制作与导出

**E01 必须：** 同一个源文件导出给多个引擎时，记录目标引擎版本、导出器版本、预设、单位／轴向处理、材质通道转换和已验证范围。每个目标的产物有独立位置或清单条目，不互相覆盖。

**E02 必须：** 不把 GLB、FBX、USD 或引擎资源文件名视为兼容性保证。分别验证所需的网格、蒙皮、动画、材质特性和外部依赖。工作台能预览的形式也可能不同于引擎最终使用的形式；插件不支持的格式可留在项目源文件区，不应伪造已入库。

**E03 应当：** 项目先建立一组可验证的示例资产作为制作基准：实际尺寸的模型、标准材质、角色测试动作或 UI 组件。源软件与引擎都用这组例子核对预设，再批量导入；不要要求每个资产作者各自猜转换方式。

## 3. 可按类型采用的技术检查

以下是通用检查契约。采用标准方案时，仅执行适用条目；只采用命名时不自动强制技术验收。具体数值写在项目约定里。每条都写明对象和检查证据，不将“命名符合”当作“资源可用”。

### 3.1 模型、模块化组件与碰撞

**Q01 必须（模型）：** 源文件约定单位、导出比例、轴向与枢轴。用已知尺寸的物体在目标引擎中核对；不依赖每次摆放时任意放大 100 倍修正错误。保留有意的实例缩放，记录镜像／负缩放的处理方法。

**Q02 必须（需要纹理采样的模型）：** 对应 UV、材质槽和纹理引用存在且实际可用。材质 UV 的有意重叠与烘焙光照 UV 的非重叠需求分开检查；不把“所有 UV 禁止重叠”套用于平铺、镜像或共享纹理。完全程序化且不使用 UV 的材质可以记录为不适用。

**Q03 应当（不同观察距离的模型）：** 根据屏幕占比与性能策略配置 LOD 或引擎等价方案，检查切换、轮廓、材质与动画是否异常。自动 LOD／虚拟几何方案可替代手工多文件；小型 UI 模型或其他无需 LOD 的用途记录原因即可。

**Q04 必须（模块化组件）：** 约定网格步长、枢轴、接口位置与尺寸。在引擎中实际拼接验证缝隙、穿插和方向；不强制跨引擎统一为某个商店的 10 单位要求。

**Q05 必须（物理交互对象）：** 有明确碰撞形状、层／过滤与用途，实际检查阻挡或触发。纯视觉对象可标明不需要碰撞。不要为“所有网格必须有碰撞”增加无用开销，也不要用渲染网格名字证明物理设置正确。

### 3.2 材质与贴图

**Q06 必须（贴图／材质）：** 检查语义与导入设置：颜色空间、normal 方向、Alpha、打包通道、粗糙度／光滑度、压缩与过滤。对照实际渲染，检查缺贴图、黑材质、反向凹凸与透明边缘。

**Q07 应当（资源预算）：** 为主要用途约定分辨率、纹素密度与内存预算。同类物体保持合理的一致性；主角、远景、UI 可使用不同档位。需要 mipmap／特定压缩／平台限制时按其要求选择尺寸；不能把所有纹理必须为 2 的幂或最大 8192 当作跨平台恒定规则。检查运行时占用，不能只看 PNG 文件大小。

### 3.3 骨架、动画、2D 与 UI

**Q08 必须（骨架／动画）：** 记录目标骨架、参考姿势、帧率、根运动策略和动作范围。共享动画验证骨架兼容性；在目标引擎播放代表性动作，检查绑定、权重、缩放、循环和根位移。命名相同不能证明可直接复用。

**Q09 必须（2D／UI）：** 记录像素密度或像素风缩放策略、锚点／枢轴、图集、九宫格（如适用）和透明边缘规则。在目标分辨率与缩放下检查裁切、拉伸、采样渗色；字体检查实际使用语言的字符覆盖。它们是对原指南 2D／UI 类型表的通用补充。

### 3.4 音频、特效与关卡

**Q10 必须（音频／特效）：** 音频确认声道、目标压缩／加载方式、循环点与项目响度约定；特效确认实际引用、粒子生命周期、材质、可见边界与性能预算。删除调试资源后再检查依赖；资源显示正常不能证明发行构建完整。

**Q11 必须（关卡／可实例化内容）：** 在实际引擎加载、实例化或运行，修复阻止加载、引用丢失和脚本／图编译错误。警告逐项处理或记录合理例外。采用烘焙流程时检查相应光照数据；纯动态流程不强制烘焙。检查可见区域的重叠闪烁、错误碰撞、导航等实际使用功能。

**Q12 应当（对外交付资源集）：** 提供可打开的 overview／demo 或同等使用示例，并检查发行包中必需依赖齐全、实验和调试文件按计划排除。只交付普通模型包时可用导入说明与已验证场景替代工程级演示。未运行的引擎或平台明确列为未验证。

## 5. 引擎事实的官方依据

适配以实际版本的文档和编辑器行为为准；本规范不是官方支持矩阵。

- [Godot 项目组织](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html)：场景附近组织资源、C# 例外、第三方内容与 `.gdignore`。
- [Godot 版本控制](https://docs.godotengine.org/en/stable/tutorials/best_practices/version_control_systems.html)：按版本区分缓存和版本控制设置。
- [Unity 资源元数据](https://docs.unity3d.com/Manual/AssetMetadata.html)：身份与 `.meta`。
- [Unity 特殊目录](https://docs.unity3d.com/Manual/SpecialFolders.html)：原生文件夹语义。
- [Unreal 资源操作](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-assets-in-unreal-engine)：通过编辑器维护资源操作与引用。
- [Unreal 资源命名](https://dev.epicgames.com/documentation/en-us/unreal-engine/recommended-asset-naming-conventions-in-unreal-engine-projects)：类型前缀；项目可选定自己的词典。
- [glTF 2.0 规范](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)：该格式中的材质、通道和颜色／数据解释；不能推定所有其他格式都采用相同约定。
